# Estate Pro Two-Factor Authentication

## Security model

Estate Pro uses TOTP as the primary second factor. The TOTP secret is generated with a cryptographically secure random source and stored only as authenticated AES-256-GCM ciphertext. The encryption key is supplied through `TWO_FACTOR_ENCRYPTION_KEY` and is never persisted in the database.

Enrollment is a two-state lifecycle: `PENDING` and `ENABLED`. A pending enrollment cannot satisfy the login challenge. The factor becomes enabled only after a valid current TOTP is verified.

## Login challenge

A successful password authentication for a 2FA-enabled user returns a short-lived MFA challenge instead of an access token or session. The challenge contains no TOTP secret and stores only a SHA-256 digest server-side. The challenge is one-time use, expires quickly, and has a bounded failure count.

TOTP verification accepts the current 30-second time step only. A successful step is persisted atomically; a step that is equal to or older than the last accepted step is rejected as replay.

## Recovery codes

Recovery codes are intended for the lost-authenticator case. Ten cryptographically random 32-character hexadecimal codes are generated by default. Only Argon2 password-hash output is persisted. The plaintext codes are returned once at enrollment or regeneration and must not be logged or stored by clients insecurely.

A recovery code is single-use. Consumption is an atomic database update, so a code cannot be reused after it has been marked used. Regeneration deletes the complete previous recovery-code set before the new hashes are persisted, invalidating every old code.

A lost-authenticator user can complete the MFA login challenge with one unused recovery code. After authentication, 2FA can be disabled with password re-authentication plus the recovery code. Regeneration of recovery codes is stricter: it requires an authenticated session, password re-authentication, and a current TOTP code, so recovery codes cannot be used to silently mint a replacement recovery set.

## Disable and audit boundaries

Disabling 2FA always requires password re-authentication and either a current TOTP code or an unused recovery code. Enrollment, enablement, disablement, recovery-code consumption, and recovery-code regeneration emit security audit events without secrets, OTP values, password material, or recovery-code plaintext.

## Brute-force controls

Enrollment verification, MFA verification, disable/re-authentication, and recovery-code regeneration are throttled at the HTTP boundary. Failed TOTP/challenge verification also updates persistent failure state and can temporarily lock verification for the configured duration.
