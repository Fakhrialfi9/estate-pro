## 364–371 — Architecture and security

### Authentication architecture

The HTTP boundary is the NestJS controller layer. `AuthController` handles login, logout and current-user reads. `LoginService` resolves the user and credential repositories, applies account-state and lockout rules, checks the password with the password hasher, creates an authentication session and issues a JWT containing the user subject and session identifier. `JwtAuthGuard` verifies issuer, audience, algorithm, signature and required claims. The session identifier is checked against the session repository before a protected request is accepted.

2FA is inserted after primary credential verification. When enabled, login returns an MFA challenge instead of an access token; `TwoFactorController` completes the challenge with a TOTP or recovery code and `LoginService` then creates the session-bound access token.

### Authorization architecture

`AuthorizationGuard` runs after JWT authentication on authorization-protected controllers. It reads permission/role requirements from decorators, resolves a fresh authorization snapshot from `AuthorizationService`, verifies required permissions and/or roles, and exposes the resolved permission codes on the request. A failed authorization requirement is returned as HTTP 403 rather than treated as authentication failure.

### User domain

`AuthenticationUser` is the aggregate root for identity and account state. Credentials, profile, security state, sessions, 2FA state, recovery codes, password-reset tokens, roles and audit relationships are separate persistence concerns. `UserManagementService` normalizes identity data, performs duplicate checks, delegates persistence to the repository, records audit events, and invalidates sessions on security-disabling changes.

### Session lifecycle

A successful password login generates a high-entropy session secret. The access token contains the session identifier and the application persists only its digest through the session repository. Sessions expose safe metadata only. Users can list their own sessions, revoke one of their sessions, or revoke all sessions. Logout revokes the current session. Password changes and account security changes revoke existing sessions.

### 2FA lifecycle

`POST /auth/2fa/enrollment` creates a pending TOTP enrollment and returns provisioning material. `POST /auth/2fa/enrollment/verify` verifies the current TOTP step and enables 2FA while issuing a one-time set of recovery codes. Login with enabled 2FA returns a short-lived challenge token. `POST /auth/2fa/verify` consumes either a TOTP code or a recovery code. Recovery codes are hashed at rest and are single-use. Disablement and recovery-code regeneration require secure re-authentication.

### RBAC model

Roles and permissions are persisted as separate entities. A role-to-permission assignment maps a role to a permission; a user-to-role assignment maps a user to a role. Controllers declare required permissions or roles with authorization decorators. The authorization service resolves the effective snapshot at request time, so changing a role assignment changes subsequent authorization decisions without relying on a stale permission list in the JWT.

### Audit model

Security-sensitive actions record an immutable audit event with action, actor/subject, resource information, result and request context when available. Passwords, access tokens, session secrets and 2FA provisioning secrets are not written to audit records. Reading audit logs itself requires `audit:read` and creates an `AUDIT_LOG_ACCESSED` event.

### Security rules

Authentication is required for protected resources. Authorization is explicit; endpoints decorated with permissions or roles reject missing authorization metadata. Passwords are Argon2-hashed. JWT verification is constrained by configured issuer, audience and allow-listed algorithms. Session identifiers are represented by stored digests. 2FA verification is rate-limited and challenge/recovery values are single-use. Input DTOs allowlist request fields and security-sensitive credential fields are not accepted by user CRUD DTOs.

## 379–383 — Actual workflows

### Login workflow

Client → `POST /auth/login` → `AuthController` → `LoginService` → user repository + credential repository + authentication security → password verification → optional 2FA challenge → `SessionService.create` → `JwtTokenService.issueAccessToken` → audit event → response.

### Password change workflow

Client → `POST /users/me/password` → `CredentialsController` → profile authentication guard → `CredentialService.changePassword` → verify current Argon2 hash → validate new password policy → update credential atomically through repository contract → revoke all existing sessions for `PASSWORD_CHANGE` → response.

### Session workflow

Access token → `JwtAuthGuard` verifies JWT and session activity → controller/use case → session repository. Logout or explicit revocation marks the session revoked; subsequent protected requests using that session fail authentication. Session listing returns the `SessionEntity.toSafeView()` representation and never returns a session secret or digest.

### 2FA workflow

Authenticated user → enrollment endpoint → TOTP secret generated and encrypted for persistence → provisioning URI returned → current TOTP code verified → 2FA enabled + recovery-code hashes persisted → login with 2FA enabled returns MFA challenge → challenge verified with TOTP or one recovery code → challenge consumed → session issued. Invalid attempts increment security counters and are subject to lock/rate-limit rules.

### Authorization workflow

Client → JWT authentication → `AuthorizationGuard` → decorator metadata (`RequirePermissions` / `RequireRoles`) → `AuthorizationService.resolve(userUuid)` → permission/role assertion → controller/use case → repository/database → response. Removing a role or role-permission assignment is reflected in the next authorization resolution and therefore blocks the protected capability.
